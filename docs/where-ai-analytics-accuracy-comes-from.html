Where AI Analytics Accuracy Comes From

An AI agent reported $220 billion in net income for U.S. banks in the third quarter of 2025. The correct figure was $79.9 billion. The query ran successfully. The agent summed a field that held year-to-date net income. The database schema gave it no indication that the figure was cumulative.

I tested three ways of handling business definitions, using the same model, data, and questions. On questions the semantic layer supported, the agent answered 70% correctly without definitions and 98% with definitions in the prompt. When code applied those same definitions, accuracy reached 100%.

With definitions in the prompt, the agent sometimes gave different answers to the same question. With the rules enforced in code, every supported question returned the same result across all three runs.

1 The experiment

I used eight quarters of public FDIC call-report data, covering roughly 4,300 to 4,600 banks per quarter. Every setup used Claude Haiku 5.5 and the same frozen data snapshot.

Setup How it worked Accuracy (168 attempts) Same result in all three runs*
No definitions The agent received table and column names and wrote SQL 70% 88%
Definitions in the prompt The agent received the same table and column names, plus formulas, units, time rules, and definitions of which banks to include. It wrote its own SQL. 98% 95%
Definitions enforced in code The agent requested metrics by name. Code applied the same definitions and wrote the SQL. 100% 100%

Both columns cover the same 56 supported questions. Accuracy is the share of 168 attempts (56 questions, three runs each) that were correct. Consistency is the share of the 56 questions that got the same result, right or wrong, in all three runs. A consistent answer can still be wrong.

I tested 58 questions in four sets. Forty-two tested one rule at a time, such as calculating quarterly income from year-to-date figures or deciding which banks count as community banks. Of those, 30 were development questions and 12 were held out. Another 16 combined several rules, such as comparing quarterly net income for community banks in one region with the same quarter a year earlier. Eight were development questions and eight were held out. Two questions required capabilities outside the semantic layer’s scope. I cover them separately below.

I wrote the held-out questions before making any changes and locked them until the final run. Each question ran three times per setup. Code graded every answer against expected results from hand-written SQL.

The prompt and enforced setups received identical definitions from a versioned file that specified formulas, reporting periods, units, and which banks to include. In the enforced setup, the agent could not query the tables directly. Through a tool, it specified the metrics, groupings, filters, and period. A Python layer used the definitions to generate and run the SQL, then returned the result. Tools such as dbt’s semantic layer, Cube, and Snowflake semantic views work on the same principle.

2 What went wrong without definitions

Without definitions, the agent still got the technical details right. It checked for missing values, made sure no bank was counted twice, and noticed that dollar amounts were stored in thousands.

Its mistakes were about business meaning, not technique. A column labeled net income does not say it holds a running total for the year. Nothing in the tables says an industry ratio should be calculated from industry totals rather than by averaging each bank’s ratio.

Asked for the industry’s return on assets in the second quarter of 2026, the agent tried three methods and got three answers:

  • 2.57%: year-to-date income multiplied by four, which overstates a second-quarter figure
  • 1.48%: a simple average of every bank’s ROA, which gives a small bank the same weight as the largest
  • 1.32%: a size-weighted average of each bank’s reported ROA, which covers the first half of the year rather than the second quarter

It chose 1.32%. The governed figure, calculated from industry totals for the quarter, was 1.30%. Without an agreed definition, the agent had no way to know which method was right.

On questions that combined several rules, accuracy without definitions fell to 42–50%, compared with 70% overall.

3 What went wrong with definitions in the prompt

With definitions in the prompt, the agent made four errors in 168 supported attempts. Each time, it had the rule it needed and failed to apply it.

  • Asked for a large holding company’s total assets, it found the company’s ID but never used it to pull all of its banks. It missed two of four and reported $426.5 billion instead of $457.4 billion.
  • Asked the same income-growth question three times, it made a different mistake in two of the runs. Once it calculated quarterly income incorrectly and reported 48.6%. Once it got the totals right but reported 3.69% instead of 103.7%, and labeled billions as millions.
  • It declined one question, saying the quarter was outside the data. The quarter was included.

The enforced setup made none of these errors. Code looked up banks by ID, checked which quarters existed, and did the calculations, so the answers were right in every run. With definitions only in the prompt, an executive could ask the same question twice and get two different figures.

The sample is small. Four errors against none does not prove a statistically significant difference. Accuracy and consistency both need testing on more questions.

4 What the enforced setup could not answer

The 100% results cover supported questions. I also included two questions designed to fall outside the layer, to see what happens at its edge.

Both asked how many banks filed a report in one quarter but not in another. Answering them requires matching individual banks across quarters. The semantic layer could produce totals and groupings, but not that comparison.

The two setups that wrote their own SQL answered both questions correctly in all six attempts. The enforced setup declined five times. In the sixth, it stated an assumption and answered 292 instead of 294. A governed layer controls how numbers are calculated, not whether the agent stretches them to answer a question they do not cover. Declining correctly has to be tested on its own.

The setup without definitions had the opposite problem: it never declined, even when it should have. Asked for quarterly income in the earliest quarter of the data, it gave a confident number in all six attempts. That figure cannot be calculated, because the data does not include the prior quarter.

This is the trade-off. A governed layer answers only what it was built for, and usually says so when it cannot. An agent writing its own SQL will attempt anything, including questions it cannot answer correctly. A bank evaluating either approach should count declined questions as well as wrong answers, and treat each decline as a request to extend the layer.

5 Right numbers, wrong conclusions

The experiment graded single numbers. Executives read conclusions, so I built a natural-language analytics app on the same semantic layer and asked it to compare peers and explain trends.

The app usually retrieved the right numbers. The errors were in what it said about them:

  • It named the wrong bank as the top performer in a peer group.
  • It stated a multiple between two banks that the numbers did not support.
  • It described a deposit share as “about 2%” when it was 0.38%.

Each fix went into code, not the prompt. Rankings are computed in code, and the app checks every “highest” or “lowest” claim against them. Every derived number must come from a calculator, and every percentage must trace to the data. U.S. territories and records without a known location stay out of peer comparisons. When one bank drives a group’s result, the app must say so. The semantic layer kept the numbers right; these checks keep the conclusions right.

After these changes, the app handled all 15 executive questions correctly in each of three runs. I used those questions while building the fixes, so the result shows the fixes hold, not how the app performs on new questions.

6 Adding the data executives ask for

The first version covered size, growth, income, and credit quality. I added funding costs, capital, and portfolio composition so an executive could use it for a fuller peer review. I also added branch data for local deposit-market comparisons.

Area What was added
Mergers Combined historical results for acquirers and acquired banks
Earnings and funding Quarterly returns, margins, and funding costs
Capital and reserves Capital ratios and allowance coverage
Deposit mix Uninsured, brokered, non-interest-bearing, time, and core deposits
Loan mix Loan categories, credit quality, and commercial real estate concentration
Market share Branch deposits, market shares, and rankings by geography

I checked the additions against published figures and reconciliation tests, keeping the original experiment’s snapshot unchanged. For the 1,054 banks over $1 billion in assets, the average gaps from the FDIC’s figures were 0.03 percentage points for quarterly return on assets, 0.07 for net interest margin, and 0.03 for cost of funds. Branch deposits matched call-report domestic deposits exactly for the bank I checked and came within 0.4% nationally. The app could now answer questions on commercial real estate and uninsured deposits that it previously declined.

The new data also brought new ways for a correct number to mislead. The app now handles three of them in code:

Deposit growth after an acquisition. Three of New England’s larger banking organizations showed 22% to 27% deposit growth over the year as reported. All three had acquired banks. Counting the acquired banks in both years, growth ranged from −2.6% to +1.0%. The layer combines the acquirer’s and acquired bank’s histories, so rankings reflect real growth, not acquisitions.

Custody deposits in a retail comparison. State Street holds 42% of Boston-area deposits, booked at a single office. These are custody balances, not branch customers. The app must explain what those balances are and name the leading branch-based banks as well.

A state’s credit figures dominated by one bank. In Rhode Island, one bank held 95% of the state’s noncurrent loans. Excluding that bank, the rate was 1.07%. The app must include this finding when explaining the statewide result.

7 Why some figures differ from earnings releases

Figures from the app will sometimes differ from a bank’s earnings release. Usually both are right: call reports describe each bank, earnings releases describe the holding company, and some ratios are calculated differently.

Balance-sheet amounts such as loans, the allowance, and brokered deposits matched published figures to the thousand. Ratios differ more. Quarterly return on assets ran 0.05 to 0.08 percentage points above the earnings release in normal quarters, and much further in merger quarters: 1.85% against 0.94% for one bank. The app flags merger quarters in its answers.

The semantic model records which ratios use bank-level data, and the app explains the difference where it matters, such as commercial real estate concentration. The front-page sample questions use balance-sheet and credit measures because those reconciled most closely.

Branch data has a similar limit. The FDIC Summary of Deposits is annual, excludes credit unions, and shows where banks book deposits, which may differ from where customers live.

8 The extended benchmark

I extended the question set from 15 to 28, adding capital, deposit mix, commercial real estate concentration, deposit market share, and a bank’s branch footprint. Each question ran three times.

The full run got 82 of 84 attempts right (98%). Both misses were the Rhode Island question. The check for one bank driving a state’s result ran when results were grouped by state code but not by state name, so two answers left the finding out.

The fix was one line in the app’s checking code. No definition or prompt changed. After the fix, the question passed all three attempts; the reported result stays at 82 of 84.

I used these questions while building the app, so the result shows the fixes hold. The next test is to freeze the app and give it questions someone else wrote.

9 What this means for bank leaders

Three steps before deploying an analytics agent:

  1. Agree on definitions first. Decide how the metrics executives use are calculated: which institutions belong in totals, how acquisitions affect growth, and whether a ratio describes a bank or its holding company.
  2. Test with real questions. Check a small set of executive questions against agreed answers, asking each more than once. Review the written conclusions as carefully as the numbers, and include questions the system should decline.
  3. Put high-stakes rules in code. Where an error could reach a board report, a financial decision, or a regulatory submission, enforce calculation and population rules in governed code. Version the definitions and retest when data or rules change.

This matters because many benchmarking questions ask for figures nobody publishes. A search tool can find a bank’s reported deposits. It cannot tell you how fast a peer group’s deposits grew after adjusting for acquisitions, or a state’s noncurrent loan rate without the bank that drives it. Those figures have to be calculated, and the answer depends on the definitions behind them.

The 15,000-character glossary in this test fit in a prompt. A bank’s full metric catalog will not. At that scale, the agent should look up the definition it needs and let code apply it.

In this test, enforcing definitions in code removed every calculation error on supported questions. It did not make the system correct by default. The definitions still had to be right, questions outside the layer still had to be declined, and the written conclusions still needed their own checks.

This was a best-case test of definitions in the prompt: they were complete and current, and I wrote them alongside the answer key. Real documentation is rarely that clean, which makes enforcing definitions in code more valuable, not less. With the same model, supplying definitions improved accuracy by about 28 percentage points. That’s where I’d invest before paying for a more capable model.
